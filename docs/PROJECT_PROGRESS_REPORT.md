# Medi-Script-AI Project Progress Report

This document summarizes what has been built so far in the project, which models have been used, why they were chosen, whether they were trained by us, what data they were trained on, the current barriers, and the practical next steps to improve the system.

## 1. Project Goal

The goal of Medi-Script-AI is to convert a prescription image into structured patient and clinical information. The current pipeline is designed around five fields:

- `name`
- `age`
- `gender`
- `symptoms`
- `medicine`

The overall design is a multi-stage pipeline:

1. preprocess the image
2. segment important handwritten regions
3. run OCR on the cropped regions
4. post-process the text using domain knowledge
5. return a structured record

## 2. What We Have Built So Far

So far, the repository contains a working end-to-end prototype with the following major pieces:

- a synthetic prescription dataset generator in `dataset_generation/generate_prescription_dataset.py`
- a segmentation module in `ml/src/rx_recognition/segmentation.py`
- an OCR module in `ml/src/rx_recognition/recognition.py`
- a post-processing module in `ml/src/rx_recognition/postprocess.py`
- an orchestration pipeline in `ml/src/rx_recognition/pipeline.py`
- a runnable demo entry point in `demo.py`

The pipeline can run locally and produce a structured output. This means the project is no longer only at the model-experiment stage; it is already integrated into a full inference flow.

## 3. Models We Have Used

### 3.1 YOLOv8n for Segmentation

**Model used**

- `YOLOv8n` from Ultralytics

**Why we used it**

- Prescription images contain a lot of irrelevant content such as logos, printed text, ruled lines, whitespace, stamps, and layout noise.
- OCR performs poorly when it is forced to read the entire page at once.
- We therefore used an object detector to first isolate the handwritten regions of interest.
- `YOLOv8n` was chosen because it is lightweight, fast, and practical for experimentation.

**How we used it**

- The model is loaded in `TrainedFieldDetector` inside `ml/src/rx_recognition/segmentation.py`.
- It predicts bounding boxes for target fields.
- Each predicted box is cropped and passed to the OCR stage.
- The current pipeline uses YOLO as the default segmentation mode.

**Did we train it?**

- Yes.

**What did we train it on?**

- We trained it on a synthetic prescription dataset generated by our own script.
- The generator creates prescription-like images and automatically produces YOLO annotations for the five target classes:
  - `name`
  - `age`
  - `gender`
  - `symptoms`
  - `medicine`

**Where was it trained?**

- On Kaggle.

**Training details**

- Base weights started from the pretrained YOLO model.
- The synthetic dataset was uploaded to Kaggle.
- The detector was fine-tuned for 50 epochs.
- The trained weights were saved locally as `runs/detect/kaggle_best.pt`.

**Current status**

- The detector works well on the synthetic-style distribution it was trained on.
- It is not yet robust enough on varied real-world prescriptions.

### 3.2 TrOCR for Handwriting Recognition

**Model used**

- `microsoft/trocr-base-handwritten`

**Why we used it**

- Standard OCR engines are weak on messy cursive handwriting.
- TrOCR is specifically designed for handwriting recognition using a transformer-based vision-text architecture.
- It is a strong baseline for handwritten English text.

**How we used it**

- The recognizer is implemented in `ml/src/rx_recognition/recognition.py`.
- Each cropped field image from the segmentation stage is converted to a PIL image.
- The TrOCR processor prepares the input image.
- The model generates text token by token.
- The generated text is returned along with a confidence estimate derived from transition scores.

**Did we train it?**

- Not yet in the current working pipeline.

**What is it trained on currently?**

- The current pipeline uses the pretrained Hugging Face checkpoint directly.
- This checkpoint was not trained by us.
- It is a general handwritten-text model, not a prescription-specific one.

**Was there a plan to train it?**

- Yes.
- The code already contains a note indicating that a fine-tuned local model could later replace the base checkpoint.
- However, as of now, the active pipeline still uses the base handwritten model.

**Current status**

- It loads and runs successfully.
- It can read some handwritten text.
- It is not yet sufficiently adapted to prescription-style handwriting, abbreviations, medicine names, and noisy crops.

### 3.3 RapidFuzz and Lexicon-Based Post-processing

**Method used**

- `RapidFuzz` fuzzy matching with a domain lexicon

**Why we used it**

- OCR output is often close to the correct answer but not exact.
- In the medical domain, even small spelling errors can be dangerous.
- We therefore added a validation and correction stage to map raw OCR text to likely valid terms.

**How we used it**

- Implemented in `ml/src/rx_recognition/postprocess.py`
- For each recognized field, the raw text is matched against a lexicon.
- If a close enough match exists, the text is corrected.
- A validation confidence is also produced and combined with segmentation and recognition confidence.

**Did we train it?**

- No. This is not a trained model.
- It is a rule-based and similarity-based correction layer.

**What data does it use?**

- A custom medical lexicon loaded through the lexicon layer.
- This includes drug names and other field-specific known values.

**Current status**

- Useful as a safety and cleanup layer.
- It cannot fix errors if the cropped region is wrong or if OCR output is completely unrelated to the correct text.

### 3.4 LocateAnything as an Experimental Alternative

**Method used**

- A local `LocateAnything` API-based segmentation route

**Why we explored it**

- The YOLO detector is trained on only five classes and a synthetic distribution.
- We wanted to test whether a prompt-driven region locator could support more open-ended real-world layouts.

**How we used it**

- Implemented experimentally in `LocateAnythingFieldDetector` inside `ml/src/rx_recognition/segmentation.py`
- The image is sent to a local API server
- The returned `<ref>...</ref><box>...</box>` predictions are parsed
- Boxes are grouped into the target field buckets

**Did we train it?**

- No.

**Current status**

- This path is experimental.
- It depends on a separate local API server not included as a working default in this repo.
- It is not the current reliable path for normal project execution.

## 4. How the Pipeline Works Today

The current live flow is:

1. `demo.py` loads a sample prescription image
2. `pipeline.py` preprocesses the image
3. `segmentation.py` uses YOLO to detect field regions
4. each crop is sent to `recognition.py`
5. TrOCR produces raw text for each crop
6. `postprocess.py` validates and corrects the text using the lexicon
7. `record.py` formats the final output into a structured record

This means the project is operational as a prototype, but its reliability is still limited by the quality of segmentation and domain adaptation.

## 5. What We Have Trained vs What We Have Not Trained

### Trained by us

- YOLOv8n detector
  - fine-tuned on synthetic prescription images generated by our dataset generator
  - trained on Kaggle

### Not trained by us yet

- TrOCR recognition model
  - currently using the publicly available pretrained checkpoint
- LocateAnything route
  - experimental external system
- RapidFuzz post-processing
  - not trainable in the same way; it is a rule- and lexicon-based step

## 6. What Is Working Well Right Now

- The end-to-end codebase is integrated and runnable.
- YOLO weights are available locally and can be loaded by the pipeline.
- TrOCR loads and performs inference correctly.
- The system produces a structured output format.
- The post-processing stage adds a useful correction layer.
- The modular design makes it easy to improve each stage independently.

## 7. Main Barrier We Are Facing Now

The main barrier is not simply that OCR is weak. The larger issue is domain mismatch between our training setup and real-world prescriptions.

### 7.1 Barrier 1: Synthetic-to-Real Gap

The YOLO detector was trained on synthetic prescriptions. Real prescriptions are much harder because they contain:

- different paper layouts
- inconsistent field ordering
- slanted handwriting
- multiple lines for a single field
- low contrast images
- blur, shadows, folds, and camera distortion
- doctor-specific writing styles
- printed and handwritten content mixed together

As a result, the detector may miss fields, crop the wrong region, or merge unrelated text.

### 7.2 Barrier 2: TrOCR Is Not Prescription-Specific Yet

The current TrOCR model is general-purpose for handwritten English, but prescriptions are a specialized domain. They include:

- rare medicine names
- short abbreviations
- dosage patterns
- incomplete grammar
- unusual uppercase and lowercase mixing
- very difficult cursive

Because of this, even a correct crop can still produce weak text recognition.

### 7.3 Barrier 3: The Current Field Design Is Too Rigid

The current system assumes exactly five fields and expects them to map cleanly to fixed targets. Real prescriptions often do not follow this assumption.

Examples:

- multiple medicines instead of one
- no explicit gender field
- symptoms implied rather than written
- extra fields like doctor name, date, dosage, advice, diagnosis, and follow-up notes

### 7.4 Barrier 4: Lack of Real-World Evaluation Data

We do not yet have a sufficiently large, properly annotated real-prescription evaluation set. Without that:

- we cannot measure actual field-level accuracy reliably
- we cannot identify failure patterns precisely
- we cannot prove generalization to unseen real prescriptions

## 8. How to Resolve These Barriers

### 8.1 Build a Real Prescription Dataset

This is the most important next step.

What to do:

- collect real prescription images with privacy-safe handling
- annotate field bounding boxes on real documents
- include wide variation in layout, quality, and handwriting style
- create train, validation, and test splits based on source diversity, not only random image splits

Why it helps:

- it directly addresses the synthetic-to-real gap
- it gives YOLO a realistic training signal
- it gives us trustworthy evaluation data

### 8.2 Retrain the Detector on Real Data

What to do:

- continue using YOLOv8n initially
- fine-tune it on real annotated prescriptions
- keep synthetic data only as a supplement, not the main source
- inspect false positives and missed boxes visually after each training cycle

Why it helps:

- better crops will improve every later stage
- segmentation quality is the foundation of the whole pipeline

### 8.3 Fine-Tune TrOCR on Prescription Crops

What to do:

- build a dataset of real cropped handwritten fields paired with ground-truth text
- include medicine names, symptoms, names, and dosage patterns
- fine-tune TrOCR on this domain-specific text

Why it helps:

- the recognizer will learn the visual style and vocabulary of prescriptions
- this should reduce character and word-level errors significantly

### 8.4 Expand the Output Schema

What to do:

- move beyond the current fixed five-field assumption
- support multiple medicine entries
- consider additional fields such as:
  - `dosage`
  - `frequency`
  - `doctor_name`
  - `date`
  - `diagnosis`
  - `advice`

Why it helps:

- the pipeline will better reflect the real structure of prescriptions
- it reduces forced mapping of text into the wrong field

### 8.5 Add Better Debugging and Evaluation Tools

What to do:

- save segmentation visualizations with predicted boxes
- save each cropped region
- log raw OCR output per crop
- compare predictions with ground truth automatically
- compute per-stage metrics

Why it helps:

- we will know whether failure comes from preprocessing, detection, OCR, or post-processing
- this prevents guessing and speeds up iteration

### 8.6 Improve Preprocessing

What to do:

- add deskewing
- improve contrast normalization
- reduce shadows and noise
- handle mobile camera perspective distortion

Why it helps:

- cleaner inputs improve both detection and recognition

### 8.7 Keep the Lexicon but Do Not Depend on It Too Much

What to do:

- continue using fuzzy matching as a correction layer
- expand field-wise lexicons carefully
- avoid treating lexicon correction as a replacement for better OCR

Why it helps:

- it remains valuable as a safety layer
- but it should support the pipeline, not carry the pipeline

## 9. Honest Current Project Status

At this stage, the project should be described as:

- a working end-to-end prototype for prescription information extraction
- strong on the synthetic workflow it was designed around
- partially functional on real prescription samples
- not yet robust enough to claim dependable performance on arbitrary real-world prescriptions

That is not a failure. It is the normal stage of a vision-and-OCR system before real-data adaptation.

## 10. Recommended Immediate Next Steps

The highest-value next steps are:

1. create a real annotated prescription dataset
2. retrain YOLO on real prescriptions
3. fine-tune TrOCR on real cropped handwriting
4. add visual debugging for segmentation and OCR crops
5. evaluate field-by-field on a real validation set

## 11. Final Conclusion

We have successfully built the architecture and the first working version of the full pipeline. The project already includes:

- a trained segmentation detector
- a working handwriting recognizer
- a medical post-processing layer
- an end-to-end structured extraction pipeline

The main limitation is that only the segmentation stage has been trained by us, and that training was done on synthetic data. The current OCR stage is still a general pretrained model, and the full system has not yet been adapted deeply enough to real prescription distributions.

To move from prototype to reliable real-world performance, the project now needs real annotated prescription data, domain-specific OCR fine-tuning, stronger segmentation training, and systematic evaluation.
